# PingLake v0.3.0 升级与回滚说明

本文说明从 v0.1.x/v0.2.0 升级到 v0.3.0 的顺序、数据库迁移、Agent 分批升级和失败回滚。v0.3.0 同时更新 Web 控制台和 monitoring schema；请先阅读并在维护窗口执行。

本文不包含任何生产密码、注册令牌、SMTP 密码或 SSH 凭据。文中 S4 Hub 和 S1–S4 Agent 的生产更新状态为 **pending**，需要在目标环境完成并记录证据后才能标记为完成。

## 1. v0.3.0 带来的变化

### 控制台

- 使用紧凑顶部导航、移动端抽屉和底部导航。
- 节点默认卡片视图，同时提供列表视图、状态/分组筛选和主机搜索。
- 主题按钮提供 Obsidian、Porcelain、Lagoon、Amber 和 system；主题不在告警设置抽屉内配置。
- 节点详情增加资源、网络、服务、探测、上报质量和监测配置页签。
- BrandMark、favicon 和 Apple Touch Icon 统一为新标记。

### 监控协议和 Agent

- monitoring schema v2 与 v1 Hub/Agent 兼容。
- 每核心 CPU、Swap、磁盘 IO/IOPS/延迟/队列、inode、网卡错误/丢弃和 TCP 状态。
- systemd/SCM 服务、精确进程名、本机 TCP/UDP 监听端口。
- ICMP、TCP、HTTP(S) 和 canonical DNS 探测。
- 采集/上传解耦、最多 64 条持久化 spool、重试、过期和丢弃计数。
- 配置 revision、Agent applied revision、质量指标和探测统计。
- 浏览器到节点 HTTPS 测点延迟。

### Hub 和数据

- schema v5 增加监控 JSON、事件表、配置版本、去重索引和告警对象。
- schema v6 增加 canonical DNS、进程、本机端口样本及索引。
- 同一报告身份的相同重试幂等；不同内容冲突会拒绝，不会静默覆盖。
- 旧 v1 报告和已有历史数据继续可读。

## 2. 升级前检查

在维护窗口开始前：

1. 记录当前 Hub/Agent 版本、二进制 SHA-256、Compose/K3s/systemd 配置和环境变量名。
2. 确认有足够磁盘空间容纳 SQLite 一致性备份、WAL 和迁移期间的临时增长。
3. 确认可以停止 Hub 写入，并准备旧 Hub 二进制、旧 Agent 二进制和可恢复数据库备份。
4. 在测试环境先执行 v4→v5→v6 迁移和恢复演练。
5. 确认管理员密码、Agent 凭据和 SMTP/Webhook 设置不会写入日志或发布说明。
6. 准备健康检查清单：Pod/服务 Ready、`/api/healthz`、登录、节点列表、SSE、历史、告警和静态资源。

## 3. SQLite/WAL 一致性备份

只复制运行中的 `pinglake.db` 不足以作为备份，因为已提交事务可能仍在 `pinglake.db-wal` 中。优先使用 SQLite online backup API；如果没有该工具，先停止 Hub，再整体复制数据库目录中的数据库、WAL 和 SHM 相关文件。

Docker Compose 示例：

```powershell
$volume = docker volume ls `
  --filter "label=com.docker.compose.project=pinglake" `
  --filter "label=com.docker.compose.volume=pinglake-data" `
  --format "{{.Name}}"
if ([string]::IsNullOrWhiteSpace($volume)) { throw "pinglake-data volume not found" }
docker compose stop hub
docker run --rm `
  -v "${volume}:/data:ro" `
  -v "${PWD}:/backup" `
  alpine:3.20 `
  tar czf /backup/pinglake-v0.2.0-before-v0.3.0-$(Get-Date -Format yyyyMMdd-HHmmss).tar.gz -C /data .
docker compose start hub
```

确认备份文件能读取、大小合理，并把备份放到与 Hub 不同的存储位置。不要提交 `.env` 或任何包含生产凭据的文件。

## 4. Hub-first 升级步骤

1. 停止 Hub 或暂停写入，完成并核对 WAL 一致性备份。
2. 保存当前 v0.2.0 Hub 二进制、容器镜像/Deployment 和配置。
3. 部署 v0.3.0 Hub，启动时允许迁移 v4→v5→v6。
4. 查看迁移日志，确认没有 schema、索引或数据校验错误。
5. 确认 Hub 服务 Ready，`/api/healthz` 返回 200。
6. 使用管理员密码登录，检查登录、节点列表、历史、告警和实时 SSE。
7. 确认 v2 Hub 在 enrollment 响应中声明 monitoring schema v2。
8. 先不要升级全部 Agent；保留一个旧 Agent 验证 v1 报告仍能被接受。

Compose 环境通常执行：

```powershell
git pull
docker compose -f docker-compose.yml -f deploy/docker-compose.tls.yml up -d --build
docker compose ps
docker compose logs --tail=200 hub caddy
```

K3s 或 systemd 环境使用相同顺序替换 Hub 二进制/工作负载，但需要同时检查实际运行进程版本和挂载路径，不能只依据旧镜像标签判断版本。

## 5. Agent 分批升级

Hub 健康后依次升级 S1、S2、S3、S4（或目标环境中的每台 Agent）：

1. 保存该节点当前配置、state 目录和旧二进制。
2. 安装 v0.3.0 Agent，保留现有 Agent ID、secret、Hub URL 和 state 目录，不重新注册已有节点。
3. 确认服务 active，版本输出为 v0.3.0，日志没有持续上传或配置错误。
4. 在 Hub 确认节点在线、最新采样时间、monitoring schema、应用 revision、队列长度和上传失败数。
5. 配置一个受控服务/探测/进程/端口检查，确认结果和历史进入 Hub。
6. 观察一个完整检查间隔和告警状态，再继续下一台。

每台都记录：

- systemd/Windows 服务状态。
- Agent 版本和二进制 SHA-256。
- 节点 online、最近心跳和最新样本。
- `applied_config_revision`、spool 队列、重试和丢弃计数。
- 服务、探测、进程、本机端口和 DNS 结果。
- Hub 端是否出现异常新增告警。

旧 Agent 与 v2 Hub 继续使用 v1 报告；新 Agent 与旧 Hub 会自动投影为 v1。不要在没有验证 Hub 的情况下先把所有 Agent 升级到 v2-only 检查。

## 6. 浏览器测点升级注意事项

浏览器到节点延迟需要每个节点有独立 HTTPS URL。升级后检查：

- Agent 的 `latency_bind` 只监听 loopback。
- `dashboard_origin` 是不带路径、凭据或尾斜杠的精确 HTTPS origin。
- 反向代理转发 `/pinglake/latency` 并关闭缓存。
- 返回 204、`Cache-Control: no-store`，只允许配置的 Origin。
- Hub CSP 包含新的测点来源；保存新 URL 后刷新页面。
- 浏览器能验证 TLS，目标网络允许该请求，其他 Origin 被拒绝。

本地 HTTP/CORS handler 测试不能替代真实公网 HTTPS、浏览器 TLS、CSP 和缓存验收。

## 8. 回滚步骤

### Hub 回滚

如果 v0.3.0 Hub 启动失败、迁移失败或关键数据不可读：

1. 停止 Hub，保留失败现场日志和当前数据库副本。
2. 不要只替换旧二进制后重启；v6 数据库不保证旧 Hub 可读。
3. 停止所有会写入该数据库的服务。
4. 恢复 v0.2.0 兼容数据库备份，包括 WAL/相关文件。
5. 恢复 v0.2.0 Hub 二进制/镜像和配置，启动并检查健康、登录、节点、历史、告警和 SSE。
6. 暂停 Agent 扩展配置，确认旧 Agent 报告正常后再决定下一次维护窗口。

### Agent 回滚

单台 Agent 异常时，停止服务，恢复保存的旧二进制并保留原 state 目录和凭据，启动后检查节点 online、最新心跳和上传错误。不要因为一次暂时的网络失败删除 state 或重新注册节点。

## 9. 发布验收标准

只有以下条件都满足，才能把 v0.3.0 标记为已发布/已生产：

- 本地 Web 类型检查、测试和构建通过。
- Rust fmt、测试、Clippy 和 release build 通过。
- v1/v2 兼容、spool、迁移、重复报告、服务/探测/进程/端口/DNS 和统计测试通过。
- Hub-first 升级和可恢复 WAL 备份已在目标环境演练。
- S4 Hub 和 S1–S4 Agent 生产版本、SHA-256、健康状态和数据上报已记录。
- 浏览器桌面/移动端、真实 HTTPS 测点和 Windows/Linux 权限检查完成。

在这些条件完成前，Release Notes 和文档只能写“生产验证 pending”，不能声称 S4 Hub 或 S1–S4 Agent 已经更新成功。
